House price prediction

Predicting sale prices for 1,460 houses in Ames, Iowa, from 79 features (the data used in Kaggle's House Prices competition). The work covers exploration, cleaning, a five-model comparison in scikit-learn, and the same pipeline rebuilt in PySpark MLlib.

  • 0.927test R², Lasso
  • $23.6ktest RMSE
  • 5models compared
ModelCV RMSE (log price)Test RMSE ($)Test R²

Approach

  • Trained on log(price), since sale prices are skewed to the right; overall quality (r = 0.79) and living area (0.71) are the strongest single features.
  • Dropped the 7 columns missing in more than 15% of rows, imputed the rest, and one-hot encoded inside a scikit-learn pipeline, so nothing leaks between folds.
  • Found that plain regression is numerically unstable on about 270 correlated one-hot columns, while Lasso and Ridge stay stable and win.
  • Rebuilt the pipeline in Spark (Imputer, VectorAssembler, StandardScaler, elastic-net regression), with the target kept out of the features.

Iris prediction API with model selection

A FastAPI service that trains two classifiers at startup and serves whichever scores higher in cross-validation. Every prediction says which model made it and when, and a feedback endpoint retrains on new labelled samples without forgetting earlier data.

  • 96.7%held-out accuracy
  • 99%test coverage
  • 8pytest tests

What it does

  • Scores Gaussian Naive Bayes (0.958) and a decision tree (0.942) with 5-fold cross-validation and serves the winner.
  • Returns flower_class, model and a UTC timestamp with every prediction.
  • Validates measurements and class labels, so bad input gets a clear 422 response.
  • GitHub Actions runs the tests with a 90% coverage gate, and a release job packages the code only after they pass.

Stack

  • FastAPI
  • Pydantic
  • scikit-learn
  • pytest
  • GitHub Actions

Wine classifier as Docker microservices

Three FastAPI services split the work of an ML system: one cleans incoming samples, one retrains the model, one serves predictions. They run together under Docker Compose and share each new model through a volume, so a retrained model goes live without restarting anything. The model predicts which of three cultivars a wine came from, using 13 chemical measurements.

  • 97.8%cross-validated accuracy
  • 98%test coverage
  • 3services
client ─POST /process─► processr :8888 ─POST /train─► trainr :7777 ─POST /reload_model─► predictr :9999
                                                         │                                  ▲
                                                         └────── models volume (shared) ─────┘

What it does

  • Keeps every feedback sample and retrains on the base data plus the full history, reporting cross-validated accuracy after each update.
  • Shares one set of Pydantic schemas across the services, rejecting negative values and unknown labels.
  • Returns a clear 502 or 503 when a downstream service or the model isn't available.
  • CI starts the whole Compose stack and sends real requests through it end to end.

DevSecOps pipeline for an ML API

A GitHub Actions pipeline that tests a containerized ML service on six platform combinations, enforces a coverage gate, scans the Docker image for known vulnerabilities, and publishes a release only after every check passes.

  • 6parallel test jobs
  • 98%coverage (95% gate)
  • 72CVEs triaged
push ──► unittest ───────────────────────────────────┐
     ├─► codecoverage  py3.10/3.11/3.12 × ubuntu/windows ┤
     ├─► container-security  build ► Grype scan ► SARIF report
     └──────────────────────────────────────────────► upload_zip (after all 3 pass)

Security findings

  • The scan of the original image found 72 vulnerabilities: 2 critical (glibc CVE-2021-33574), 6 medium, 6 low and 58 negligible.
  • All of them were in Debian packages from the base image, none in the app's own code, and none had an upstream fix.
  • The remedy was a newer slim base image, a non-root user and a smaller image, plus a script that turns each SARIF report into a severity table and chart.
